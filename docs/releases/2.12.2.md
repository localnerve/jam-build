# v2.12.2 — JSON-LD Data Islands for Agentic Browsing

This release adds **per-page JSON-LD structured data** to every rendered page, generated at build time from `site-data.json` — the same source of truth that renders the human markup. One dataset produces two outputs: what people read and what machines parse. The motivation is **Agentic Browsing**: AI agents increasingly fetch pages directly instead of routing through search APIs, so structured data that lives in a separate CMS pipeline drifts from the page it describes. Deriving it at build time makes that drift structurally impossible — the island can't disagree with the HTML because they share an origin.

Correctness is enforced by a **four-layer defense**. Layers 1–3 land in this release; layer 4 (scheduled checks of live production URLs) is deferred.

## New

- **JSON-LD data islands** — `src/build/jsonld.js` builds a schema.org graph per page: shared `Organization` and `WebSite` nodes (defined once, referenced everywhere by `@id`), a page-specific node whose type is resolved through a small builder registry (`WebPage`/`AboutPage`/`ContactPage` via `NAV_TYPE_BY_NAME`), and a `BreadcrumbList` for every non-home page. Output is inlined as `<script type="application/ld+json">` markup, wired through `src/build/index.js`, `src/build/templates.js`, and the page header partial. Pages typed `admin` or `none` (internal surface + error pages) intentionally emit no island — they are not meant to be indexed.
- **Layer 1 validation — internal graph consistency (`validateGraph`)** — runs on every local build via `loadJsonLd()`. Walks each page's graph for dangling single-key `@id` reference stubs that don't resolve to an in-graph node, missing `@type`, and nodes with neither `name` nor `url`. Advisories print as warnings locally; passing `{ strict: true }` turns the same checks into a hard build failure. This is the "see it the moment you edit" signal — no extra tooling required.
- **Layer 2 validation — schema.org vocabulary drift (type-level)** — `schema-dts` added as a devDependency and the builder functions annotated via JSDoc (`@returns {import('schema-dts').Organization}` etc.) with a per-file opt-in `// @ts-check` pragma on `jsonld.js`. A separate `tsconfig.lint.json` (allowJs, checkJs off globally, strict, noEmit, nodenext) is wired in as the third stage of `npm run lint` via `lint:types`. When `schema-dts` bumps a major version tracking a spec revision, re-running `tsc` surfaces exactly what changed underneath you — "did the spec change" is outsourced to a dependency instead of hand-tracked.
- **Layer 3 validation — consumption correctness against real validators (CI)** — `src/build/jsonld-validate.js` (script `npm run jsonld:validate`) extracts every emitted island from `dist/*.html`, flattens each `@graph`, and validates it against the live schema.org vocabulary plus Google Rich Results requirements using `@adobe/structured-data-validator`. The vocabulary is fetched from schema.org on each run, with a local cache fallback so an offline run degrades to last-known-vocabulary rather than failing. Errors fail the build; optional-field warnings are reported but non-fatal.
- **Strict CI build flag** — `--strict` is threaded through the existing gulp arg parser into both `loadJsonLd` call sites, mirroring the `args.dump` pattern. CI now runs `npm run build -- --strict` (hard-fail on graph issues) followed by `npm run jsonld:validate`, while local dev builds stay advisory.

## Changed

- **Container-type exemption in `validateGraph`** — `BreadcrumbList` nodes carry their identifying data on child `itemListElement` entries, not a top-level `name`/`url`. They are now exempt from that check (via a `CONTAINER_TYPES` allow-list), restoring signal purity: the advisory no longer fires on every non-home page for a node that is spec-correct as emitted.
- **CI verification pipeline** — `.github/workflows/verify.yml` build step renamed to "Check Production Build (strict JSON-LD)" and now passes `--strict`; a new "Validate Structured Data in Built HTML" step runs the Layer 3 check after the build.

## Deployment Notes

- No change to real deployment behavior beyond the new structured data now appearing in built pages. The islands are inert data (`<script type="application/ld+json">` is not executable script), so they sit outside CSP `script-src` and do not require or break the CSP hashing in `html.js`.
- `npm run jsonld:validate` runs **after** `npm run build` and defaults to the `dist/` directory (`npm run jsonld:validate [distDir]`). It requires network access to schema.org for a fresh vocabulary; without it, it falls back to a self-maintained, persistent cached copy in `tmp/schemaorg-latest.json`.
- New development dependencies for json-ld validation and drift protection:
  * `@adobe/structured-data-validator`
  * `schema-dts`
  * `typescript` - Used as a type linting tool, not a language extension (files opt-in w/`// @ts-check`)
